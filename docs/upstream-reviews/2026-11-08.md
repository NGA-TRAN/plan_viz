Continue to the feature designs with updated evidence about metric scope and
execution semantics. The inspected changes do not establish a need for a broad
visualization upgrade first. plan-viz consumes exported plans; it does not embed
the Rust DataFusion engine, so upgrading that engine is not an npm dependency
update in this repository.

Prioritize preserving query/section/stage/task metadata before implementing
metric displays. Keep existing visualization defaults. This review changes
documentation only and proposes follow-up work, not a new visual design.

**Status:** initial compatibility triage complete for the ranges below;
implementation and broader semantic validation remain open. The DataFusion
unreleased-main examination is a watchlist, not an exhaustive support audit.

## DataFusion Distributed main: findings

### Metrics need explicit scope and provenance

- **Workers aggregate by name before collection by default.** Partition IDs and
  other labels can be removed; per-task export still supplies `task_id`.
  The old per-partition collection can be selected through
  `with_distributed_aggregate_metrics_on_workers_before_collection(false)`.
  Wenqi's model must not invent partition detail from task totals. This is an
  unreleased-main change after our audit, not a proven setting of the user's
  supplied digests. [Upgrade contract](https://github.com/datafusion-contrib/datafusion-distributed/blob/64a0a13d59d27f5facb05838d47adb2afe8a843d/docs/upgrade/5.0.0.md#7-worker-metrics-are-aggregated-per-task),
  [collection source](https://github.com/datafusion-contrib/datafusion-distributed/blob/64a0a13d59d27f5facb05838d47adb2afe8a843d/src/worker/impl_coordinator_channel.rs).
- **Snapshots are authoritative for reported metric families.** The metrics
  wrapper keeps local-only families, rather than reintroducing raw local
  partitions for a family already reported by a worker. This matters when
  distinguishing observations and avoiding duplicate attribution.
  [Wrapper implementation and tests](https://github.com/datafusion-contrib/datafusion-distributed/blob/64a0a13d59d27f5facb05838d47adb2afe8a843d/src/execution_plans/metrics.rs).
- **Task completion can contribute stage/task metrics.** `TaskFinishedHandler`
  receives succeeded, failed or incomplete outcomes; a handler can return custom
  metrics. The upstream example prints `finished_tasks={0:1, 1:1, 2:1}` on stage
  headers. Our parser retains it in the whole raw document but has no structured
  stage-metric field. A complete-plan probe reproduced that gap. These custom
  metrics are not guaranteed outcome metadata on every exported plan.
  [Handler](https://github.com/datafusion-contrib/datafusion-distributed/blob/64a0a13d59d27f5facb05838d47adb2afe8a843d/src/events/task_finished.rs),
  [example test](https://github.com/datafusion-contrib/datafusion-distributed/blob/64a0a13d59d27f5facb05838d47adb2afe8a843d/tests/task_finished_handler.rs).
- **Final collection includes failure/cancellation paths.** A terminal snapshot
  is not proof that all input was consumed. Keep completion state explicit when
  available and unknown otherwise. This reinforces the earlier metrics research.
  [Collection change](https://github.com/datafusion-contrib/datafusion-distributed/commit/fb90a4d40bc1509f6c06d561c3d3f592793e1f69).
- **Iceberg adds `files_opened` and `bytes_scanned`.** Files count when the reader
  starts work, including read-ahead that may never yield output under a limit.
  Bytes reflect the reader's bytes-read accounting and can be nonzero with no
  output rows. Treat these as source-specific I/O metrics, not memory usage.
  [Recording sites](https://github.com/datafusion-contrib/datafusion-distributed/blob/64a0a13d59d27f5facb05838d47adb2afe8a843d/iceberg/src/common/scan_config.rs),
  [tests](https://github.com/datafusion-contrib/datafusion-distributed/blob/64a0a13d59d27f5facb05838d47adb2afe8a843d/iceberg/tests/scan_metrics.rs).
